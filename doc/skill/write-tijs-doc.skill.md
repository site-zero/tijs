# 编写 TiJS 文档（write-tijs-doc）

> 任务：在 `doc/reference/` 下新增或修订 TiJS 文档；以及判断一篇内容该写到哪里。
> 先按「第 0 步」判断类型与归属，再选对应模板写作；写完按第 8 节做同步检查。
> 本规范只约束 `doc/` 体系；组件源码旁的 `types/api/example` 不在此列。

---

## 第 0 步：判断文档类型与归属

一篇文档只干一件事，不要混型：

| 你要讲的内容 | 落到哪里 |
| --- | --- |
| 某个机制为什么存在、怎么运转（组件模型、i18n、样式、字典模型…） | `doc/reference/10.concepts/` |
| 某个 core 命名空间提供哪些 API、怎么调用 | `doc/reference/20.core-utils/` |
| 某个组件怎么用：Props、Events、示例 | `doc/reference/30.components/<类>/<组件>.md` |
| 某个 composable hook 的机制与用法 | `doc/reference/40.features/` |
| 如何完成一类工程任务（新增组件、写测试、发布、写文档本身） | `doc/skill/` |
| 通读源码过程中的阶段性认识、踩坑、待办 | `doc/note/`（不发布站点，可能过时） |

**边界**：参考手册里不写操作教程；技能文档里不展开机制原理（一句话带过 + 链接到 reference）。

## 1. 目录归属速查

`doc/reference/` 的分区与收录范围（骨架见根 `README.md`）：

- `00.start-here/` —— 新读者入门：是什么、安装引导、跑通第一个组件。
- `10.concepts/` —— 全库共同地基：`TiComInfo`/`TiComRace` 组件模型、共享 Props、事件绑定、
  i18n、样式体系、字典模型。这里只写一次，组件篇与工具篇引用，不重复展开。
- `20.core-utils/` —— `src/core/` 各工具命名空间，**一个命名空间一篇**。
- `30.components/` —— 75 个注册组件，按六类分子目录：`action/` `edit/` `input/` `shelf/`
  `tile/` `view/`；每个组件一篇。
- `40.features/` —— `src/lib/_features/` 每个 hook 一篇，按主题分子目录归档。
- `101.dev/` —— 源码布局、新增组件流程、测试、构建发布、代码规范。

新增主题时优先挂进已有分区；确需新分区，先在 `doc/reference/README.md` 讨论确认，不要私自新建顶层目录。

## 2. 通用前置规则

1. **以源码为准。** Props、Events、默认值、行为边界一律从 `src/` 源码抽取；文档与源码
   冲突时改文档（源码是真相）。禁止凭印象写、禁止从网络旧教程照抄。
2. **清单唯一。** 75 个组件的全量清单只维护在 `30.components/README.md`；组件篇不重复罗列
   其他组件；数字（组件数、导出函数数）必须现扫源码得出，不手抄旧文档。
3. **共享内容只写一次。** `CommonProps`、i18n 规则、样式变量体系在 `10.concepts/` 讲透；
   组件篇、工具篇只写一句「详见 `xx-xx.md`」并链接，不复制粘贴。
4. **读者先于实现。** 文档面向使用 TiJS 的二次开发者与 AI Agent：先回答「是什么、怎么用、
   有什么坑」，内部实现细节只在需要解释行为时点到为止。
5. **语言口径。** 叙述用中文；类型名、Props 名、事件名、文件路径、代码块保持英文原样；
   代码示例里的注释用中文。

## 3. front-matter 规范

`doc/reference/` 下每一篇都必须带 YAML front-matter，只保留检索需要的三个字段；
源码路径、模块归属、相关文档一律写进正文末尾的「延伸阅读」，不进 front-matter。

缺 front-matter 的篇目视为未完成。

```yaml
---
title: TiButton 按钮                          # 文档标题，与正文 H1 呼应
keywords: [按钮, button, TiButton, action]    # 5~8 个检索词，中英都放
status: draft                                  # draft | done | deprecated（默认 draft）
---
```

字段说明：

- `keywords`：AI 检索的唯一抓手，组件名、中文俗称、英文俗名、近义词都放进去。
- `status`：`draft` 草稿、`done` 完成、`deprecated` 已弃用；弃用组件标 `deprecated`。

**正文末尾固定设置「## 延伸阅读」小节**，承载两类链接：

- **源码入口**：按「注册表 → 类型 → 视图 → api/support」顺序列出相对路径，便于核对实现：
  `src/lib/action/button/ti-button-index.ts` …
- **相关文档**：列出相邻主题文档的相对链接，一句话说明关联点。

## 4. 各类文档结构模板

### 4.1 概念机制篇（`10.concepts/`）

适用：组件模型、共享 Props、事件绑定、i18n、样式体系、字典模型。

```markdown
# <机制名称>概述

## 要解决的问题
（没有这套机制会怎样、什么场景触发；一段话说清动机，从读者会遇到的问题切入。）

## 解决思路
（核心设计：先给一张 ASCII 分层图或数据流图，再逐层讲清入口 → 出口；
这是全文最重要的一节。）

## 关键细节
（边界行为、默认值、竞争条件、容错与常见误区；一条一个无序列表项。）

## 主要代码入口
（类名/函数名 + 一句话职责；只列读源码时的入口，不贴大段代码。）

## 延伸阅读
- [相关手册](相对路径.md) — 一句话说明为什么相关
```

要求：概念篇只回答「解决什么问题、思路是什么」，不堆 API 清单；配置、用法、完整示例
一律下沉到对应专题篇，概念篇留链接。

### 4.2 core 工具命名空间篇（`20.core-utils/`）

适用：`Str`、`I18n`、`DateTime`、`Dicts`、`Match`、`Tmpl`、`Net`、`Num`、`TiStore`、
`Util`、`Alg`、`G2D`、`Web`、`_top`。

```markdown
# <命名空间>概述

## 职责
这个命名空间解决什么问题，与相邻命名空间如何分工。

## 导出清单
按功能分组列出函数/类/类型；表格每格不超过 20 字符，长对照改用无序列表：
- **函数名**：一句话职责（签名见源码导出）。

## 典型用法
至少一个完整可核对的例子；优先改写自 `src/test/core/` 中已有的测试用例。

## 注意事项
边界行为、空值处理、时区/编码等易混点。

## 延伸阅读
```

### 4.3 组件篇（`30.components/<类>/<组件>.md`）

75 个组件统一按此模板批量生产，保证口径一致。**参数一律用分组无序列表，不使用
Props 表 / Events 表。**

````markdown
---
title: <组件中文名>
keywords: [...]
status: draft
---

# <TiXxx> 中文名

## 介绍
控件设计用于什么场景、什么交互形态；使用时需要注意什么。一句话标注 `race`
（INPUT/EDIT/SHELF/ACTION/TILE/VIEW…）与源码目录。

## 例子
先给一份最小可用配置，同时给出两种调用形态：

### JSON 配置

```json
{ }
```

（schema / 动态渲染视角的 `comConf` 对象，可直接放进示例注册表。）

### Vue 标签调用

```xml
<TiXxx ... />
```

（等价的 `<TiXxx ... />` 模板写法；Vue 标签片段一律用 `xml` 代码块高亮。）

## 控件参数
六个固定小节，按属性归属拆分；某一小节没有内容就写「本组件无此组参数」，
不要省略小节标题。

### 数据
进入 / 带出控件的值与展示内容（如 `value`、`text`、选项来源、模型值）。
- **`prop`（类型，默认值）**：说明含义与取值。

### 行为
影响交互与处理流程的开关与处理规则（如 `readonly`、`autoI18n`、`stopPropagation`、
`mustInOptions`）。
- **`prop`（类型，默认值）**：说明。

### 外观
只控制视觉表现的属性（颜色、字号、间距、尺寸、对齐、边框、宽高）。
- **`prop`（类型，默认值）**：说明。

### 回调
允许用户注入的函数、渲染器、子控件定义。
- **`prop`（类型）**：说明调用时机与参数。

### 嵌套
子控件 / 插槽的放置位置；控件通常提供同名 slot。无插槽的组件明确写出
「本组件未提供插槽，内容由数据属性决定」。
- **`<slot-name>`**：说明放置内容。

### 事件
组件对外声明的标准 Vue `emit` 事件，无序列表，不另列事件表。
- **`event-name`**：载荷形态 + 触发时机。

> 继承的共享 Props（`CommonProps`、`ReadonlyProps`、`PlaceholderProps` 等）不在本篇
> 罗列，只用一句话指向 [共享 Props](../../10.concepts/02-common-props.md)。

## 更多例子
逐个对应 `ti-xxx-index.ts` 中的 `exampleProps`（`example/ex-*.ts`），示例名与注册表
保持一致。每个示例先给 `json` 围栏的 `comConf`，再给 `xml` 围栏的等价 Vue 标签；两个
围栏块前各占一行加粗引导语（`**JSON 配置**`、`**Vue 标签**`），引导语与代码块之间留空行，
避免两个围栏块在部分 Markdown 预览器里紧贴在一起。

## 总结
一段话收束：适用边界、与相邻控件如何选择、已知限制。

## 延伸阅读
- **源码入口**：注册表、类型、视图、api/support 等相对路径。
- **相关文档**：相邻组件、对应 feature hook 的相对链接，一句话说明关联点。
````

写作要求：

- 参数从组件 `ti-xxx-types.ts` 的 `XxxProps` 逐一抽取；必填/可选、默认值、联合类型
  都要核对源码，不得省略可选标记；归属分组拿不准时按上面的分组定义判断，写进文档前
  回看组件 `TiXxx.vue` 的实际消费方式。
- 事件从 `XxxEmitter` 与 `emits` 声明抽取，说明载荷形态与触发时机；被 `action` 类
  回调接管、不再 `emit` 的分支必须写明。
- 示例优先直接复用 `example/*.ts` 的 `comConf`；确需补例，必须先在源码中核对可运行性，
  不允许写跑不通的伪配置。
- 一个组件一篇；同目录多个变体（如 `TiForm` 与 `TiTabsForm`）各占一篇，互相链接。
- 分类理由与组件索引见 `30.components/README.md`。

## 5. 组件源码解剖约定（写组件篇前先按这套找素材）

每个组件目录的固定组成（以 `src/lib/input/text/` 为范本）：

| 文件/目录 | 作用 | 文档素材来源 |
| --- | --- | --- |
| `ti-xxx-index.ts` | `TiComInfo`：`icon`/`race`/`name`/`i18n`/`install`/`defaultProps`/`exampleProps` | 中文名、race、示例清单、liveStyle |
| `ti-xxx-types.ts` | `XxxProps`、`XxxEmitter`、`XxxApi` | 六组参数无序列表、事件清单 |
| `TiXxx.vue` | 视图模板与状态接线 | 事件接线、插槽、样式类 |
| `ti-xxx-api.ts`（如有） | `useXxxApi`：组件内部计算与操作 | 行为边界、注意事项 |
| `example/` | `ex-*.ts`：`ComPropExample` 演示配置 | 文档示例 |
| `support/`（如有） | 内部辅助逻辑 | 实现细节，需要时引用 |
| `i18n/`（如有） | 组件局部语言包 | 文案键，不在组件篇重复翻译 |
| `style/`（如有） | 组件样式 | 样式体系文档引用，不在组件篇展开 |

注册表查询 API 不要在组件篇重复介绍：`installTiComponents`、`tiGetComponent`、
`tiFindComponents` 等机制属于 `10.concepts/01-component-model.md`。

## 6. 叙事风格

以「让读者顺着顺序顺利读完」为目标，不写成干巴巴的说明书。

### 6.1 读者画像（作者内部准则，不写进正文）

动笔前作者自己先在心里回答两个问题，**这一节的结论永远不出现在交付给读者的文档里**：

- **读者是谁、已经会什么**：默认读者是掌握 Vue 3 基础、了解基础 HTML/CSS 的二次开发者，
  会模板、`props`、`emit`、`flex` 布局；不假设他懂组件库设计、schema 动态渲染或 TiJS
  自有约定。次要读者是阅读源码的 AI Agent。
- **要把他带到哪里**：本篇结束时读者应能回答哪个问题、学会哪个用法。

**搭桥规则**：从读者**已知**的知识（Vue 3、原生表单、基础 CSS）起笔，逐步引到 TiJS 的
**未知**概念（注册表、共享 Props、字典、事件回写）。正文第一行就应落在读者熟悉的具体
场景或已知概念上，随后用自然过渡引出不熟悉的内容。

**禁止出现的元叙述**：正文不得写「我们假定你是……」「读者画像」「你已经会什么 / 暂时
不需要什么」这类对文档本身的说明；读者读到的应该直接是内容，而不是关于读者的讨论。
概念篇分区 README 先讲项目初衷与目标场景，再进入机制。

### 6.2 行文纪律

- **从读者的问题出发**：开篇先站在读者想完成的事情里（「想给输入框加一个只读状态，
  不用每个组件自己判断」），核心答案独立成行、加粗揭晓；概念在读者需要时才命名。
- **一次只引入一个新概念**：第一个例子保持最小形态，下一个例子只改动一处；不要把
  Props、事件、样式、字典一次性压进「最小例子」。
- **先看到它工作，再讲怎么构造**：先给出可跑的配置与结果，内部 API 退后展开。
- **关键句独立成段并加粗**：核心结论独占一行制造停顿；段落保持短小。
- **用读者被例子催生的疑问做过渡**：「看懂这个例子后，你自然会问……」，不要提前喊口号。
- **从已知出发**：按 6.1 的画像，先锚定 Vue 3、原生 HTML 表单等读者已懂的知识，
  再引出 TiJS 特有的约定；不要反过来默认读者已经懂组件库设计。
- **不过早展开细节**：每写一段自问——只掌握前文的读者读到这里会不会困惑；会就先铺垫，
  细节挪到后续专题篇。
- **ASCII 图优先**：讲分层、数据流、目录关系时，一张图胜过三段文字；先给图再解释。
- **诚实说明边界**：当前实现的限制要明说；已知待删除组件（`TiFilter`、`TiComboFilter`、
  `TiFilterBar`）在清单中标 `deprecated`，不写使用教程。
- **收束要准确**：结尾回扣主线，用机制实际做的事描述，不拟人化、不草率下结论。

## 7. 格式与命名

- 文件一律 **kebab-case**：`02-common-props.md`，不用下划线或空格。
- 标题层级：H1 一篇一个；`##` 分主节，`###` 分小节；「延伸阅读」与正文平级用 `##`。
- 表格只用于每格 ≤ 20 字符的简单对照；长字段、长说明改用无序列表 `- **键**：说明`。
- 代码块必须标注语言：` ```ts `、` ```xml `（Vue 模板/标签片段统一用 `xml` 高亮，
  视觉效果优于 `vue`）、` ```scss `、` ```bash `。
- 相对链接用仓库相对路径；文件名改动后，全库扫描 `](*.md)` 相对链接并修复，
  正文中残留的旧文档链接一并清理。
- 不写 HTML 注释占位；未完成篇目 `status: draft`，不要在正文留 TODO 空话。

## 8. 写完必做的同步清单

1. `doc/reference/INDEX.md`：在对应分区加一行
   `- [标题](相对路径.md)：一句话说明这篇写什么。`
   链接文字用可读标题，不写裸路径；抽象名称（如「组件模型」「字典模型」）后面必须补一句
   短句，让不熟悉主题的读者知道本篇覆盖什么；检索词留在正文 front-matter 的 `keywords`，
   不堆在索引行里。
2. `doc/reference/SOURCEMAP.md`：按本篇「延伸阅读 · 源码入口」登记「源码路径 ↔ 文档」。
3. 所属分区的 `README.md` 控件索引：新增/删除组件时同步计数与列表；组件篇全部建成后再补
   上相对链接。
4. 自检死链：本篇链接到的文档存在，正文中没有残留旧文档链接。
5. 若改动了已 documented 行为的源码，回到本篇校对 Props、Events、示例是否仍然成立。

当前阶段 `INDEX.md`、`SOURCEMAP.md` 先手工维护；篇目稳定后再考虑写脚本从 front-matter 生成。

## 9. 禁止事项

- 不臆造 Props、事件、默认值与示例；源码里读不到的，标「待补充」而不是编造。
- 不照搬 `doc/_old/`、历史草稿或网络旧文档（本仓库目前没有旧草稿，未来归档后同样禁止照抄）。
- 不在概念篇罗列 API 清单；不在组件篇复制共享 Props 清单；不在工具篇讲组件用法。
- 不为 `deprecated` 组件写新增使用教程，只标注状态与替代项。
- 清单数字不手抄；组件数、hook 数、导出函数数都以当前源码扫描结果为准。
